# 美業 SaaS 多租戶權限架構與客戶歸屬權討論記錄

**文件日期**：2026-02-13  
**參與者**：Project Manager (AI), User  
**狀態**：架構確認 (暫不開發)

## 1. 核心議題：客戶歸屬權 (Customer Ownership)

在美業生態中，「客人屬於誰」是最敏感的商業問題。系統必須能彈性支援不同的商業模式。

### 三大核心情境

| 情境 | 商業模式 | 資料歸屬邏輯 | 系統實作對應 |
| :--- | :--- | :--- | :--- |
| **情境 A** | **傳統連鎖 / 雇傭店** | **歸屬公司 (Tenant)** | 所有客戶資料屬於 Tenant，員工離職無法帶走。 |
| **情境 B** | **共享工作室 (合夥)** | **歸屬個人 (User)** | 設計師 A 看不到 設計師 B 的客人，資料嚴格隔離。 |
| **情境 C** | **混合模式 (靠行)** | **混合歸屬** | 區分「店客」(歸店) 與「私客」(歸人)。 |

## 2. 帳號與租戶架構 (Tenant & User Model)

為解決上述歸屬權與隱私問題，我們確認了以下 SaaS 帳號架構邏輯：

### 模式一：合夥拆帳 (獨立型)
*   **需求**：合夥人 A 與 B 想完全獨立，帳目分開，客人不互通。
*   **解法**：**購買兩套系統 (Two Tenants)**。
    *   Tenant A (Owner: Partner A)
    *   Tenant B (Owner: Partner B)
*   **優點**：權限與財務絕對乾淨。
*   **代價**：
    *   需要付兩份系統費。
    *   若共用櫃台，切換帳號操作繁瑣。
    *   若共用 LINE OA，無法自動分流預約。

### 模式二：合夥共營 (共享型)
*   **需求**：合夥人 A 與 B 互相信任，想一起拚業績，節省成本。
*   **解法**：**購買一套系統 (One Tenant)**。
    *   Tenant A (Owner: Shared / Partner A 代表)
    *   User A (Admin)
    *   User B (Admin)
*   **優點**：成本低，協作方便，資料共享。
*   **風險**：
    *   若未來拆夥，資料歸屬權易有糾紛 (詳見潛在漏洞 2)。
    *   操作責任需透過 Log 釐清。

### 模式三：雇傭關係 (標準型)
*   **需求**：老闆請員工。
*   **解法**：**一套系統 (One Tenant)**。
    *   Tenant A (Owner: Boss)
    *   User (Boss) -> 建立 -> User (Employee)
*   **邏輯**：
    *   老闆擁有最高權限 (Root)。
    *   員工帳號由老闆發放與管理。
    *   員工離職，老闆直接停用帳號，資料留在店裡。

## 3. 潛在漏洞與風險控制 (Risk Management)

雖然架構邏輯完善，但在實際營運層面存在以下人性與操作漏洞，需在未來開發時補強：

### 漏洞 1：責任歸屬不清 (Rogue Admin Risk)
*   **風險**：若老闆知道員工密碼 (例如由老闆設定)，當發生資料刪除或帳目篡改時，老闆可推卸給員工，反之亦然。
*   **解法 (未來開發)**：
    *   系統僅發送「邀請連結」或「一次性密碼」。
    *   員工首次登入 **強制修改密碼**。
    *   確保老闆無法查看員工當前密碼。

### 漏洞 2：合夥拆夥的數據綁架 (Data Hostage)
*   **風險**：共用 Tenant 的合夥人鬧翻，主帳號管理者惡意刪除對方資料。
*   **解法 (法務/運營)**：
    *   **ToS 條款**：明確定義「付費簽約者」擁有數據所有權，系統商不介入內部糾紛。
    *   **技術備份**：實作 **Audit Log (操作日誌)** 與 **Soft Delete (軟刪除)**，保留證據與恢復能力，防止惡意破壞。

### 漏洞 3：多租戶的入口衝突 (Entry Point Conflict)
*   **風險**：模式一 (獨立型) 下，兩位合夥人共用一個店面與一個 LINE OA，導致顧客預約與櫃台作業混亂。
*   **解法 (營運建議)**：
    *   強烈建議共用櫃台/LINE 的合夥人採用模式二 (共享型)。
    *   若堅持獨立，需告知將面臨營運效率降低 (雙 LINE 帳號、切換系統) 的成本。

### 漏洞 4：資料外洩 (Data Leakage)
*   **風險**：員工離職前大量匯出或抄寫客戶資料。
*   **解法 (權限控管)**：
    *   預設關閉一般員工的「匯出」權限。
    *   敏感資料 (如電話) 進行 **遮罩處理 (Masking)**，需點擊並記錄 Log 才能查看明碼。

## 4. 結論 (Conclusion)

目前系統將優先實作 **「單一租戶 (Single Tenant) MVP」**，預設權限為 **「全店共享」**，以滿足最普遍的雇傭與緊密合夥模式。上述進階權限與多租戶隔離邏輯，將列為 **V2.0 企業版** 的核心功能。
